## これは CI の合否ではない

CLAUDE.md「CI が判定しないこと」で、**動いている場面の画素比較は禁止**されている。
ここで撮る絵と数字は、**人間と `visual-judge` が見た目を採点するための材料**で、
`npm run verify` からは呼ばない。数字を通したことは「実機で良く見える」ことを
意味しない。最後は人間が実機で決める。

## 撮りかた（決定論）

```
npm run visual:shot                     capture/visual/current/ に7場面
npm run visual:shot -- --out baseline    baseline として撮る
npm run visual:shot -- --verify          2回撮ってバイト単位で一致するか見る
```

- `__peekaboo.freezeAt(id, seed, sec)` が rAF を止め、更新時計を 0 に戻してから
  ちょうど `sec` ぶん進めて1枚描く。**壁時計を読まない**
- 種は 20260907 固定、2.00秒の時点、412×839・DPR 1
- **場面ごとにページを読み直す**（続けて切り替えると three の `generateUUID()` が
  消費した乱数の回数が変わり、触っていない場面の飾りまでずれる）
- **使う前に必ず `--verify` を通すこと。** 2026-09-07 の実測で 21枚すべて
  バイト単位で一致した

場面ごとに3枚撮る:

| ファイル | 中身 |
|---|---|
| `<id>.png` | ふつう |
| `<id>.solid.png` | 接地影だけ消したもの |
| `<id>.bg.png` | 隠れ場所ごと消したもの（背景と飾りだけ） |

`solid − bg` が**隠れ場所そのものの画素**、`solid − ふつう` が**接地影の効き**。
位置と半径から矩形を推し量ると隣とぶつかるので、**消して撮って差を取る**。

## 数値の基準（`npm run visual:score`）

隠れ場所1つごとに測り、**場面の点は「いちばん悪い隠れ場所」、
全体の点は「いちばん悪い場面」**。

| id | 何を測るか | 向き | 基準 |
|---|---|---|---|
| V1 | 輪郭の明度差の第10百分位（L\*） | 高い | **≥ 8.0** |
| V2 | 内部の L\* の四分位範囲 | 高い | **≥ 8.0** |
| V3 | 内部で最も多い L\* の帯（幅2）の占有率 | 低い | **≤ 0.35** |
| V4 | 隠れ場所の平均彩度 − 背景画の平均彩度（C\*） | 0 に近い | **|ΔC\*| ≤ 12** |
| V5 | 接地の暗さ（下の帯を影がどれだけ暗くするか、L\*） | 高い | **≥ 3.0** |
| V6 | 輪郭のうち明度差が 6 未満の割合 | 低い | **≤ 0.15** |

なぜこの6つか:

- **V1・V6 は「見える」の下限。** 背景に馴染ませる改善は、やりすぎると
  1歳半が隠れ場所を見つけられなくなる。馴染ませる方向の変更は必ずここが止める
- **V2・V3 が「のっぺり」。** 平らに塗った面は L\* が数個の値に固まる。
  形に沿った陰影があると幅が出る。**ノイズや輪郭線で稼げない**ように、
  分布の幅だけを見て勾配の大きさは見ない
- **V4 が「チープ」。** 背景画は人が描いたもので、この app の絵の基準。
  そこから彩度が大きく浮くとプラスチックに見える
- **V5 が「浮き」。** 接地影がどれだけ効いているか
